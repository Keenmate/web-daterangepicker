📱 Responsive & Mobile

Device-adaptive presentation, modal positioning, viewport-tier widths, full-screen phone sheets, and container-responsive compaction.

RS01 · Device-Adaptive Presentation — the device ladder

You usually don't need to pick a presentation by hand. A floating picker adapts to the device automatically via presentation="auto" (the default): floating on desktop, a centered modal on tablets, and an edge-to-edge full-screen overlay on phones. The classification comes from @keenmate/web-components-core and is capability-based and orientation-robust — it uses the shorter viewport side, so a landscape phone still reads as a phone.

DeviceDetected whenPresentation
Phonetouch-primary & shorter side < 600pxfullscreen (edge-to-edge)
Tablettouch-primary & shorter side ≥ 600pxmodal (centered dialog)
Desktopfine pointer (mouse), any widthfloating (anchored popover)
  • auto (default) — the ladder above.
  • floating / modal / fullscreen — force that presentation on any device (handy for previewing the phone sheet on desktop, which is what the toggles on this page do).

Because full-screen is usually a phone-only look, every demo defaults to auto and offers a Preview as full-screen toggle so you can see the overlay here on desktop. Close the sheet with the ✕ in its header, Escape, or the phone Back gesture.

Open devtools, toggle the device toolbar, and pick a phone preset — this floating picker opens full-screen.

<!-- auto (default): floating on desktop, modal on tablets, fullscreen on phones --> <web-daterangepicker selection-mode="range" visible-month-count="2"></web-daterangepicker> <!-- force one presentation everywhere --> <web-daterangepicker presentation="floating"></web-daterangepicker> <web-daterangepicker presentation="fullscreen"></web-daterangepicker>

RS02 · The Problem with Floating Mode on Small Screens

Floating mode anchors the calendar popover to its input. For multi-month layouts (visible-month-count="3", 2×3 grid, etc.), the calendar can be wider than the viewport itself — users get a horizontal scrollbar, the picker overflows the screen edge, and on mobile it becomes unusable.

The modal presentation renders the calendar as a centered overlay with a backdrop scrim instead. It works at any viewport width, scales the configured layout responsively, and locks body scroll while open.

RS03 · Opting In: presentation="modal"

Set presentation="modal" on a floating picker and it opens as a centered overlay on every device (the old positioning-mode="modal"). Closes via Escape, backdrop click, Apply (range mode), or after a complete selection.

<web-daterangepicker selection-mode="range" presentation="modal"></web-daterangepicker> // Open programmatically document.querySelector('#picker').isOpen = true;

RS04 · Modal Width Tiers

The modal's outer width adapts to viewport size, picking from four CSS variables. Breakpoints align with the rest of the codebase (480 / 768 / 1200, same as base.css and the Responsive Sizing demo's --drp-rem scaling).

Tier Viewport Default Variable
xs ≤ 480px calc(100vw − 2 × gap) --drp-modal-width-xs
sm 481–768px calc(100vw − 2 × gap) --drp-modal-width-sm
md 769–1200px 900px --drp-modal-width-md
lg ≥ 1201px 1100px --drp-modal-width-lg

Override per-instance via the host element. The breakpoints themselves are hardcoded in modal.css because CSS media queries cannot read CSS variables — only the widths inside each rule are variable-driven.

/* Custom widths per tier */ web-daterangepicker { --drp-modal-width-md: 75vw; --drp-modal-width-lg: 1300px; } /* Other modal hooks */ :root { --drp-modal-gap: 16px; /* viewport-edge gap */ --drp-modal-backdrop-bg: rgba(0, 0, 0, 0.45); /* scrim color */ --drp-modal-transition: 0.15s ease-out; /* fade timing */ --drp-z-index-modal: 9800; --drp-z-index-modal-backdrop: 9700; }

RS05 · Progressive Inner-Content Layout

Beyond just sizing the outer modal, the inner multi-month layout scales based on the modal's actual width via CSS container queries. The visible month count and grid columns adapt without any JS.

Modal width Flex layout (single row) Grid layout
≤ 600px 1 month visible (siblings hidden) 1 column (siblings hidden)
601–900px 2 months visible 2 columns, all months visible (wraps to more rows)
901–1200px 3 months visible up to 3 columns (capped from configured)
> 1200px Configured count Configured grid as-is
Why grid keeps all months visible: a 2×3 configuration is a deliberate layout choice — collapsing it to "show fewer months" would surprise the user. Instead, narrow grid modals just stack the same months into more rows (2×3 → 3×2 at 601–900px, etc.). Only at the very narrow ≤600px tier do we hide siblings, since 6 months stacked vertically would be unusably tall on a phone.

Hidden columns (when present) still update in lockstep through the existing collision-resolve navigation logic — range selection across "more months than are visible" continues to work; the user just navigates time linearly with the visible month's prev/next.

RS06 · Modal Behavior Details

  • Closes on: Escape, backdrop click, Apply button (commit-mode="apply"), or completing a selection (when commit-mode="selection", the default).
  • Body scroll is locked while the modal is open. Reference-counted so multiple modal pickers don't fight over document.body.style.overflow.
  • Input is blur()-ed when the modal opens. This suppresses the mobile soft keyboard, which would otherwise overlap the modal. Focus is restored to the input on close.
  • Sticky regions inside the modal: per-month headers stay pinned to the top of the scrolling months area, the action bar (Today/Clear/Apply) stays pinned to the bottom. Days scroll between them; the action bar is always reachable.
  • shouldCloseOnScroll is a no-op in the modal presentation — you're meant to scroll inside the modal, not have it close on you.

RS07 · Full-Screen: soft keyboard on phones (fullscreen-autofocus)

By default the keyboard stays closed when the full-screen sheet opens — it shows the calendar first, so you tap dates and the bottom action row stays reachable. Set fullscreen-autofocus to focus the input on open instead (pops the keyboard for type-to-fill, like a native picker).

Both pickers use presentation="auto": a floating popover here on desktop, a full-screen sheet on a phone — where the keyboard difference actually shows. Tick Preview as full-screen to see the overlay on desktop.

<!-- default: keyboard stays closed, calendar visible --> <web-daterangepicker></web-daterangepicker> <!-- opt in to focus the input + soft keyboard on open --> <web-daterangepicker fullscreen-autofocus></web-daterangepicker>

RS08 · Full-Screen: type dates in the header (show-fullscreen-input)

In the full-screen sheet the trigger field normally sits behind the overlay, so there's nothing to type into. show-fullscreen-input moves the real input up into the sheet header — visible, above the calendar, and wired to the same mask. It gets inputmode="numeric", so phones show a digits-only keypad: you type 08192026 and the mask fills in the separators (08/19/2026). You never need the / or . key a numeric keypad hides — the component owns them.

Pair it with fullscreen-autofocus to pop that keypad on open for a type-first flow, or leave autofocus off and let users tap the header field when they want to type. The header input takes over the row, so it's shown instead of labels.fullscreenTitle.

<!-- typeable input in the full-screen header, numeric keypad + mask --> <web-daterangepicker show-fullscreen-input></web-daterangepicker> <!-- type-first: also pop the keypad on open --> <web-daterangepicker show-fullscreen-input fullscreen-autofocus></web-daterangepicker>

RS09 · Full-Screen: header heading (labels.fullscreenTitle)

The full-screen header shows just a close (✕) button by default. Set the fullscreenTitle label for a heading beside it — useful to label what the user is picking.

<web-daterangepicker labels='{"fullscreenTitle":"Choose your dates"}'></web-daterangepicker>

RS10 · Forcing a Presentation

Set presentation to a concrete value to override the device ladder on any device — for a deliberate design choice or to inspect the phone/tablet UI on a desktop.

Phone detection needs a viewport meta: your page must include <meta name="viewport" content="width=device-width"> — without it a mobile browser lays out at ~980px and the picker classifies the phone as a tablet (modal instead of full-screen).

RS11 · Container-Responsive Compaction: compact-below

The modal tiers above react to the viewport. But a picker placed in a narrow sidebar or a resizable panel on a wide monitor has a small box while the viewport is still large — viewport media/container queries on the modal don't help an inline picker sitting in a column. compact-below keys off the element's own border box (via a shared ResizeObserver in @keenmate/web-components-core), so it reacts to its container, not the window.

When the element's box drops below the threshold, the calendar collapses to a single month and hides the Today / Clear buttons. Widen it back and the authored layout returns verbatim — and any selection you've made survives the transition.

Below 520px the two-month layout collapses to one and the action buttons drop away. Pick a range first, then resize across the threshold — the selection is preserved.

<web-daterangepicker selection-mode="range" positioning-mode="inline" visible-month-count="2" compact-below="520"></web-daterangepicker>
CSS container queries first. compact-below exists for the structural change — swapping the month-column count is a JS decision the engine can't do with CSS alone. For purely presentational tweaks under a narrow box (padding, a label→icon swap, stacking the summary), reach for container-type: inline-size + @container in your own CSS instead; it's cheaper and paints without a rebuild. Leave compact-below unset (or 0) to disable the behavior entirely — it's opt-in and never changes an existing picker's layout on its own.

RS12 · Responsive Rules: map, callback, instance override

Tune any input per device class without writing viewport code: a map ({ mobile: {…}, tablet: {…}, desktop: {…} } — keys are core classifyDevice classes) or a callback returning a partial config. Rules live page-wide (window.components.responsive), per tag (window.components['web-daterangepicker'].responsive) or on the instance (el.responsive / the responsive JSON attribute, el.responsiveCallback). Resize the window across 768px / 1024px or switch devtools to a phone / tablet preset — the readouts below update.

#Layer (later wins, key by key)
1–2page-wide map → page-wide callback
3–4per-tag map → per-tag callback
5attributes / properties set on the instance
6–7instance map → instance callback (an instance rule returning null ignores every page rule)
1 month + modal on phones, 2 months on tablets, 3 on desktop

keyed on the width breakpoint, not the device class

no attribute — the page rule (presentation: 'modal') wins over the default

presentation="floating" written on the element — page rules never override it

<!-- instance map, as a JSON attribute (or el.responsive = {…}) --> <web-daterangepicker selection-mode="range" responsive='{"mobile":{"visibleMonthCount":1,"presentation":"modal"},"tablet":{"visibleMonthCount":2},"desktop":{"visibleMonthCount":3}}'></web-daterangepicker> // instance callback — ctx: { env, deviceClass, breakpoint, element, component, config (base) } const rule /* : DateRangePickerResponsiveCallback */ = (ctx) => ({ visibleMonthCount: ctx.breakpoint === 'desktop' ? 2 : 1 }); document.getElementById('rules-callback').responsiveCallback = rule; // per-tag page rule (callbacks can scope by ctx.element) window.components['web-daterangepicker'].responsiveCallback = (ctx) => ctx.element.closest('#rs-page-rule') ? { presentation: 'modal' } : undefined; <!-- an attribute on the instance beats every page rule --> <web-daterangepicker presentation="floating"></web-daterangepicker>
Overrides never reflect to attributes (getAttribute('presentation') stays as authored) and never count as "explicit"; el.presentation / el.config report the effective value. A key a rule stops returning goes back to its base value. Typed with DateRangePickerResponsiveMap / DateRangePickerResponsiveCallback; full contract in web-components-core docs/SPEC.md §6.7.
